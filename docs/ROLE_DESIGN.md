# 사역 역할·관리자 권한 개편안

2026-10-20 사용자 설명과 추가 답변 기준. 로컬 구현 완료 후 운영 적용 전 검토 문서이다.

## 최종 정정 기준 (14번이 아래 13번 초안을 대체)

- 교역자도 담당 파트만 열람한다. 다른 파트 보고/이슈는 해당 담당 교역자 또는 담임목사님·사모님이 특정 교역자에게 공개해야 볼 수 있다. 공개받은 사람은 열람·목회 피드백만 가능하며 수정·검토·재공개 권한은 얻지 않는다.
- 작성자는 직책이 아니다. 배정된 파트에서는 팀원·파트총괄·기술팀 담당자·교역자 모두 본인 보고를 작성하고 확인 전 수정할 수 있다. 타인 보고 수정·확인은 담당 교역자 이상이다. 팀원은 본인 보고만, 비목회 총괄은 해당 파트 보고 열람만 추가된다.
- 공지의 수신 직책은 전체 구성원 / 담임목사님·사모님 / 담당 교역자 / 파트총괄·기술팀 담당자 / 팀원이다. 실제 선택한 파트와 직책을 함께 검사하고, 공지 수신은 보고 열람 권한을 부여하지 않는다. 기능 관리자 역할은 사역 직책이 아니다.
- 같은 날짜·예배·팀에 여러 보고를 작성할 수 있다. 새 보고에는 작성자 이름이 반드시 필요하며 로그인 계정·당시 입력한 이름·담당 파트·최종 수정 계정을 별도로 보존한다. 다른 사람이 수정해도 최초 작성자 이름을 바꿀 수 없다. 기존 보고 이름은 프로필에서 채우며 원본 내용과 시각은 보존한다.
- 회의 자료의 종합 요약은 권한으로 걸러진 제출 보고를 같은 파트/날짜/예배 아래 모아 담당자별 사역 내용·예배 결과·설교·활동·특이사항·요청을 보여준다. 이번 주 해결된 사건과 경미한 이슈도 포함하고 이전 주 미해결을 계속 표시한다. 기도제목과 비공개 글은 별도 열람 범위를 유지하며 인쇄에서 제외한다.
- 13번과 14번을 함께 적용한 뒤 앱을 배포한다. 실제 계정의 최상단 역할/담당 배정은 별도 확인하며 기존 관리자를 임의로 최상단으로 올리지 않는다. 사용자 본인의 유일한 관리자 계정에는 명시된 관리자+교역자 조합을 적용한다.

아래 표와 상세 기록은 13번 구현 당시의 초안 이력이다. 상충하는 부분은 위 최종 기준을 따른다.

## 역할 기준

| 역할 | 내용 열람 | 작성·수정 | 코멘트 | 관리 기능 |
|---|---|---|---|---|
| 담임목사님·사모님 | 비공개 포함 전체 보고·이슈 | 작성·수정·확인·개별 공개 | 가능 | 가능 |
| 교역자 | 전체 일반 보고·이슈, 담당 파트를 우선 표시 | 일반 보고 작성·수정·확인 | 가능 | 별도 관리자 역할이 있으면 가능 |
| 파트총괄·기술팀 담당자 | 담당 파트 일반 내용 | 열람만, 작성·수정·확인 불가 | 불가 | 없음 |
| 팀원 | 본인이 작성한 보고의 확인·수정에 필요한 범위 | 본인 보고 작성·수정 | 불가 | 없음 |
| 기능 관리자 | 관리자라는 이유로 내용 열람을 허용하지 않음 | 실제 보고 수정 권한 없음 | 불가 | 사용자·파트·예배·설정·기능 점검 |

한 사람이 관리자와 교역자 역할을 함께 가질 수 있다. 사용자 본인은 이 조합에 해당한다. 역할과 별개로 승인/비활성 및 알림 허용 조건을 유지한다.

## 확정한 비공개 열람 기준

1. 기도제목과 수신인별 비공개 글은 작성자, 담임목사님·사모님, 담당 교역자에게 공개한다. 관련 없는 교역자, 중단 역할, 기능 관리자에게는 숨긴다.
2. 담임목사님·사모님은 특정 보고의 기도제목/담임목사님께 드리는 글/사모님께 드리는 글을 각각 특정 교역자에게 추가 공개하고 취소할 수 있다. 보고 전체 공개로 다른 항목까지 열리는 방식은 사용하지 않는다.
3. 중단 역할은 해당 파트 열람만 가능하다. 수정·확인과 목회 피드백은 교역자 이상이다.

코멘트는 공지의 일반 댓글과 구분해 보고/팀 이슈에 대한 목회 피드백으로 취급한다. 일반 댓글까지 모두 같은 제한을 적용할지는 기능 명칭과 실제 흐름을 함께 정리한다.

## 구현 방향

- 계정의 사역 역할과 `is_admin`을 별도 축으로 둔다. 기존 관리자에게 사역 역할을 자동 부여하지 않는다. 역할별 보고 열람·수정·확인·피드백·설정 관리 함수와 RLS를 각각 정의한다.
- ‘담당 파트 우선’은 교역자의 전체 열람을 제한하는 조건이 아니라 홈과 목록의 정렬·기본 필터다.
- 현재 담당 배정은 기존 그룹/상위 그룹 소속을 사용한다. 영상팀의 교육부서 예배별 세부 배정과 기간별 자동 로테이션은 별도 추가 작업이며 이번 마이그레이션은 일정 자동화를 만들지 않는다. 교대 시 소속은 관리자가 변경한다.
- 관리자 점검은 내용이 없는 설정/상태 또는 가상 자료 미리보기로 구성한다. 관리자 권한만으로 service role을 이용해 보고 내용을 반환하는 경로를 만들지 않는다.
- 권한 지정 기능에서 본인의 내용 열람 역할을 임의로 올리는 경로도 점검한다. 계층 변경과 담당 배정에 대한 권한 검증을 DB에서 시행한다.
- 팀 이슈 피드백은 통합 이슈 ID에 연결해 관련 팀에서 같은 코멘트를 확인한다. 작성 UI 숨김뿐 아니라 서버 액션과 INSERT RLS로 발신자를 제한한다. 피드백 수신자가 읽을 범위와 수정·삭제 권한도 테스트한다.
- 기존 계정/작성자/보고/이슈/피드백을 보존하는 새 마이그레이션과 역할 조합별 테스트를 작성한 뒤 승인받아 운영 적용한다.

## 개편 전 확인된 차이

- `is_admin()`이 `can_view_group`, `can_write_group`, `can_review_group`, 경위서 열람 등에서 내용 권한의 우회 조건으로 쓰인다.
- `reports_select`는 같은 파트 소속이면 다른 팀원 보고까지 허용한다.
- `report_comments_insert`는 보고 열람자 모두에게 작성 권한을 준다. UI도 보고자에게 작성 폼을 표시한다.
- 홈/회의 자료/이슈 작성 진입에서도 관리자 여부를 내용 접근 권한으로 간주한다.
- 현재 소속 역할은 writer/reviewer 두 가지뿐이며, 전체 열람 교역자와 기간/예배별 담당 구분은 없다.

## 구현과 운영 전환

- 13번 `20261027000000_roles_feedback.sql`이 `profiles.is_minister`, 권한 함수/RLS, `private_shares`, `incident_comments`를 추가한다. `recipient_role` 지정 계정은 최상단이며 기존 지정을 보존한다. 관리자에게 교역자 역할을 자동 부여하지 않는다.
- 담당 교역자는 `is_minister=true`와 해당 그룹 또는 상위 그룹의 `reviewer` 소속을 함께 가진다. 동일한 `reviewer` 소속이라도 교역자가 아니면 중단의 읽기 권한만 갖는다.
- 최상단만 교역자·최상단 역할을 지정한다. 기능 관리자가 본인 소속을 변경해 내용 권한을 얻는 경로는 DB 트리거로 막는다. 관리자+교역자도 본인 담당 파트는 최상단이 지정한다.
- 보고/이슈 피드백은 작성자와 최상단이 삭제할 수 있다. 과거 팀원이 남긴 댓글은 보존하되 새 작성 권한은 교역자 이상으로 제한한다. 공지의 일반 댓글은 기존 소통 기능으로 유지한다.
- 담당 밖의 교역자가 일반 보고를 수정할 때 숨겨진 기도제목을 빈 값으로 덮어쓰지 않는다. 수신인별 글 수정은 원작성자 경로를 유지한다.
- RLS를 우회하는 `TRUNCATE` 권한은 클라이언트 역할에서 회수한다. `public`/`auth` 객체는 변경하지 않는다.
- 운영 적용은 아직 하지 않았다. 적용 전에 최상단 계정과 사용자 본인의 관리자+교역자 조합, 각 교육부서 담당 교역자 배정표를 확인해야 한다. 기존 `reviewer`를 일괄 교역자로 승격하지 않는다. 최상단 계정이 아직 없다면 최초 한 번 승인받은 운영 SQL로 지정해야 한다.
- DB 적용 후 앱을 배포한다. 앱만 먼저 배포하면 새 프로필 컬럼과 RPC가 없어 동작하지 않는다. 로컬 권한 테스트 통과는 실제 운영 로그인·모바일 화면·푸시 수신 검증과 구분한다.
